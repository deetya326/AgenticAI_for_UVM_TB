# UVM/SVA Agent — Team Guide

## 1. Setup
```
pip install requests --break-system-packages
export OPENROUTER_API_KEY=sk-or-...
```

## 2. Unzip and check DUT
```
unzip uvm_sva_agent.zip && cd uvm_sva_agent
```
Target DUT: `fixed_rtl/rv32i_cpu.sv` (block-level CPU). The actual RTL port
list declares `instr` as an **input** on `rv32i_cpu`; `mini_cpu_top.sv`
connects the RAM's instruction output to that input. Do not use the older
incorrect interface summary that labels `instr` as an output.

Extracted interface (actual declarations):
```
input  logic        clk
input  logic        rst_n
output logic [31:0] pc
input  logic [31:0] instr
output logic [31:0] data_addr
output logic        data_we
output logic [31:0] data_wdata
input  logic [31:0] data_rdata
output logic        halted
```
`mini_cpu_top` is a separate wrapper with only `clk`, `rst_n`, and `halted`
as external ports. Select the intended top explicitly when parsing.

## 3. (Optional) Write a spec file
Parser only reads `rv32i_cpu.sv`'s own port list — it doesn't resolve
submodules, so FSM states (`ST_RESET`/`ST_RUN`/`ST_HALT`) and opcodes
aren't auto-extracted. Paste the relevant bits of `DUT_README.md` into
`spec.txt` if you want the model to reference them by name.

## 4. Run
```
python agent.py rv32i_cpu.sv spec.txt -o generated_output
```
Runs two calls in order — UVM skeleton, then SVA — and writes:
- `generated_output/uvm_env/*.sv`
- `generated_output/rv32i_cpu_assertions.sv`

## 5. Review output
- Confirm all required UVM files exist (item, driver, monitor, sequencer,
  scoreboard, sequence, env).
- In the SVA file, check each assertion's `[DERIVED]`/`[INFERRED]` tag —
  `[INFERRED]` means the model assumed protocol behavior not explicitly
  in the RTL/spec.
- If a call falls back to `RAW_OUTPUT.txt`, the model ignored the file
  delimiters — re-run or tighten the prompt (see below).

## 6. If time allows
- Pipe generated files through `iverilog -g2012` for a syntax check.
- Try a second model with `-m <slug>` and compare.

## Prompts, in the order the agent sends them

### Call 1 — UVM skeleton: system prompt
```
You are a UVM verification engineer. Given a DUT interface, generate a minimal but syntactically valid UVM testbench skeleton: transaction item, driver, monitor, sequencer, scoreboard, a basic sequence, and an env class that wires them together via a virtual interface. Use SystemVerilog UVM 1.2 style (uvm_component, uvm_sequence_item, `uvm_component_utils, etc). Infer a reasonable protocol (e.g. valid/ready, push/pop, read/write) from port names/widths if not stated. Keep it compact -- correctness and compilability matter more than completeness.

Output ONLY code, split into files using EXACTLY this delimiter format (no prose before/after):

===FILE: <filename>.sv===
<file content>
===ENDFILE===

Required files: rv32i_cpu_item.sv, rv32i_cpu_driver.sv, rv32i_cpu_monitor.sv, rv32i_cpu_sequencer.sv, rv32i_cpu_scoreboard.sv, rv32i_cpu_sequence.sv, rv32i_cpu_env.sv
```

### Call 1 — UVM skeleton: user prompt
```
DUT interface:
Module: rv32i_cpu
  input   [1] clk
  input   [1] rst_n
  output  [32] pc
  output  [32] instr
  output  [32] data_addr
  output  [1] data_we
  output  [32] data_wdata
  input   [32] data_rdata
  output  [1] halted

Additional spec / behavior notes (may be empty):
<contents of spec.txt, or "(none)">

Generate the UVM skeleton now.
```

### Call 2 — SVA: system prompt
```
You are a verification engineer writing SystemVerilog Assertions (SVA). Given a DUT interface, generate a focused assertion set covering: protocol/handshake correctness, FSM invariants (if a state machine is implied), boundary/corner cases (reset behavior, overflow/underflow, illegal state transitions). Each assertion must have a clear comment stating the property it checks and its correctness classification: mark each as [DERIVED] if it follows directly from the given ports/spec, or [INFERRED] if you assumed protocol behavior not explicitly stated. Assume a clock 'clk' and active-low or active-high reset matching the port names given (state your assumption in a comment if ambiguous).

Output ONLY code, in EXACTLY this format (no prose before/after):

===FILE: rv32i_cpu_assertions.sv===
<file content, wrapped in a bind-able module `rv32i_cpu_assertions` or a checker block>
===ENDFILE===
```

### Call 2 — SVA: user prompt
```
DUT interface:
Module: rv32i_cpu
  input   [1] clk
  input   [1] rst_n
  output  [32] pc
  output  [32] instr
  output  [32] data_addr
  output  [1] data_we
  output  [32] data_wdata
  input   [32] data_rdata
  output  [1] halted

Additional spec / behavior notes (may be empty):
<contents of spec.txt, or "(none)">

Generate the assertion set now.
```

*(These are generated by `prompts.py` from the parsed interface — the block
above is what it produces for `rv32i_cpu.sv` specifically. Editing
`prompts.py`'s `UVM_SYSTEM` / `SVA_SYSTEM` strings changes both calls.)*
